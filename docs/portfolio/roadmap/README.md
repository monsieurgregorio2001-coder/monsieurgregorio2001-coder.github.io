## Portfolio investment rules

Fix broken delivery, confusing claims, missing contact/resume access, and unreadable proof first. Carry the confirmed [positioning](positioning.md) through the concept, selection, language, and finish of each slice; ask for evidence of judgment and collaboration rather than adding those words as unsupported claims. Make each lead project explain problem, individual contribution, architecture/tradeoff, verification, limitation, and result. Keep employment claims separate from demo capabilities.

Default recommendation: reach a credible release with the existing static hub, unless Garfield chooses a bounded Five Rooms slice that fits the same readiness budget. This is an agent recommendation, not an approved redesign direction. Missing V3 images and the Kuru rename remain optional unless the chosen release genuinely depends on them.

Timebox initial portfolio work to the first week's proposed six hours. If the gate cannot pass, record the actual blocker, avoid sending a broken portfolio link, and replan a smaller proof path. After readiness, spend most time finding fit and applying. Add a feature or new project only when repeated job requirements or interview feedback expose a specific proof gap.

## Dependencies, risks, and responses

| Risk / dependency | Response |
| --- | --- |
| Missing candidate constraints | Research and fix portfolio while waiting; do not guess eligibility, pay, or start-date answers |
| Stale or contradictory project claims | Keep one dated evidence source per claim, rerun the relevant check or use a narrower defensible statement |
| Private production work cannot be shown | Use permitted anonymized architecture and scoped ownership explanations; do not disclose employer data or fabricate a public production repository |
| Endless redesign | Ship the minimum hiring release, keep a bounded improvement list, and revisit only from hiring evidence |
| Job disappears or changes | Recheck official posting before packet completion and submit; record closed/changed source without counting an application |
| Duplicate or uncertain submission | Deduplicate by employer/requisition; record submitting before the final action; reconcile uncertain outcomes before retry |
| Too many active packets/interviews | Limit to two tailoring packets plus one portfolio slice; prioritize due interviews and time-sensitive qualified jobs |
| Tracker or documents become public accidentally | Keep live operations in the local private workspace and review exact paths before any commit/upload |
| Handover loses local files | Transfer the private workspace and uncommitted repository work explicitly; a public repo clone alone is insufficient |

## Review and change control

Use the [success measures](success-measures.md) for a short weekly review: what was sent, what progressed, where fit or evidence was weak, and what changes next. Change one major variable per comparable cohort when practical. Small samples and pending applications are not evidence that a strategy failed.

Update this roadmap only when strategy, scope, capacity, or milestone definitions change. Keep current execution in `_career/NOW.md`, statuses in the tracker, and material decisions in an ADR or private decision note as appropriate. Begin with the plain local tracker; do not build a custom ATS, dashboard, or external workflow integration before actual volume makes it useful. The goal is interview and offer progress, not completing a documentation collection.
